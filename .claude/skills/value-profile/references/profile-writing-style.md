# Profile中文写作与术语规则

本文件在写Part 0和Part 1-5前读取。目标是让profile像研究员自己会写的分析笔记，
既有事实和判断，也有自然的阅读节奏，而不是英文分析的直译或AI处理记录。

## 1. 英文缩写白名单

正文仅保留业内已普及的缩写:

- 估值指标:ROE/ROIC/ROA/DCF/PE/PB/PS/PEG/EV/EBITDA
- 时间和比率:CAGR/YoY/QoQ/TTM
- 用户指标:MAU/DAU/ARPU/LTV/CAC
- 集中度和规模:CR5/CR10/GMV
- 宏观和合规:GDP/ESG/IPO/A股/H股/SKU
- 管理和指标:KPI/OKR/ABT

白名单外的英文默认翻成自然中文。没有固定译法时使用描述性短句,不得保留生硬英文或自造缩写。

## 2. 常用术语

| 英文 | 中文 |
|---|---|
| CFO/NI/CapEx/FCF | 经营现金流/净利润/资本开支/自由现金流 |
| NOPAT/WACC | 税后经营利润/加权平均资本成本 |
| TAM/SAM/SOM | 潜在市场规模/可服务市场规模/实际拿下市场规模 |
| SG&A/COGS | 销售管理费用/营业成本 |
| DSO/DPO/DIO | 应收/应付/存货周转天数 |
| framework/guidance | 框架/指引 |
| checklist/summary/scope/benchmark | 清单/摘要/范围/基准 |
| actual/forecast/narrative/reference | 实际/预测/叙述/参考 |
| bear/base/bull case | 悲观/中性/乐观情景 |
| stakeholder/SOE | 利益相关方/国企 |
| product/channel/revenue mix | 产品/渠道/收入结构 |
| red flag/green flag | 风险信号/积极信号 |
| M&A | 并购 |

## 3. 状态词

template是状态词的唯一来源。常见误译按下表修正:

| 不使用 | 使用 |
|---|---|
| clean/清洁 | 无触发/零触发项/合规 |
| clean audit/干净审计 | 标准无保留审计意见 |
| healthy/健康 | 财务稳健/结构稳健 |
| risk-free/无风险 | 未识别重大风险 |
| green flag/绿灯 | 积极信号/正面信号 |
| red flag/红旗 | 风险信号/警示项 |

若需要新增状态词,先修改template schema,不得在单个profile中临时创造。

## 4. 证据进度的自然中文

用户可见中文不得使用“闭合”描述证据、调查、结论或问题状态。`close/closed/closure`
是内部流程概念，写入profile、子skill报告或控制台摘要时必须按具体语义改写：

| 英文或内部含义 | 用户可见中文 |
|---|---|
| evidence complete / closed | 证据完整 / 已核实 / 已完成判断 |
| partially closed | 已核实部分信息 / 部分完成 |
| not closed | 证据仍不完整 / 仍缺资料 / 尚不能判断 |
| close a gap | 补齐资料 / 完成核验 / 处理完这个问题 |

不要机械替换成同一个词。事实已经查清用“已核实”；检查流程已经做完用
“已完成判断”；关键材料缺失用“仍缺资料”或“尚不能判断”。说明还缺什么时，
直接写明缺少的资料或尚未完成的核验，不使用抽象的流程术语。

## 5. 情景和敏感性测算的自然中文

用户可见的敏感性分析要按“假设、结果、限制”来写：

1. 说明这是**按明确假设简单测算**，并写出被调整的变量。
2. 给出**计算结果**及其对利润、现金流或估值的具体影响。
3. 列出关键**未考虑因素**，并说明结果**不是预测**，也不代表公司实际应当采用该假设。

英文中的`mechanical`通常表示只按公式计算、其他条件保持不变。中文应直接交代
假设和限制，不用带有“机械”的组合词代替说明。

## 6. 隐藏证据层元数据

引用、置信度和管理层口径校核属于证据层，用于证据追踪、进度恢复和内部复核，不是
面向投资者的正文。字段继续保存在Markdown对应section中，HTML阅读版统一隐藏；文末
证据索引继续保留，供需要追溯的读者查阅。

本文件只规定这些字段如何写入研究源文件。最终读者投影、自动删除、控制台报告和
HTML renderer边界统一见`references/reader-rendering.md`，不得在正文写作阶段为了
渲染方便而删除恢复信息。

`机器引用清单`同样写入HTML注释，同时保留原标记：

```markdown
<!-- **机器引用清单:** `C25-IP`、`C25-CF`。 -->
```

隐藏字段前先检查信息是否只存在于元数据中。若口径差异、证据冲突或未知项会改变投资
判断，把这一层含义改写进正文，例如“海外和新品类已经带来增长，但持续性仍待观察”；
不要只留下“置信度：中”或“管理层口径校核”供读者自己猜。

不得删除证据层字段，也不得把字段移出对应section。

## 7. 层级收入表

同一分类维度含父子关系时，使用三列层级明细表，不把每个层级横向展开：

```html
<p class="table-heading">
  <strong>按业务划分</strong>
  <span class="table-meta">YYYY年 · 亿元</span>
</p>
<table class="hierarchy-table">
  <thead>
    <tr><th>收入类别</th><th>收入</th><th>占总收入</th></tr>
  </thead>
  <tbody>
    <tr class="hierarchy-group"><td>父项</td><td>100.00</td><td>100.0%</td></tr>
    <tr class="hierarchy-subtotal">
      <td class="hierarchy-level-2">二级子项</td><td>80.00</td><td>80.0%</td>
    </tr>
    <tr>
      <td class="hierarchy-level-3">三级子项</td><td>50.00</td><td>50.0%</td>
    </tr>
    <tr class="hierarchy-total"><td>合计</td><td>100.00</td><td>100.0%</td></tr>
  </tbody>
</table>
```

规则：

- 表题右侧统一写`报告期 · 金额单位`，金额列只保留数字。
- 固定使用收入类别、收入、占总收入三列。
- 父子关系通过首列的`hierarchy-level-2`或`hierarchy-level-3`缩进表达。
- 金额和占比分列，不写成`金额 / 占比`。
- 不使用每层单独一列、`rowspan`、数字层级列或占位短横线。
- 产品、渠道、地区等交叉维度分表展示。只有混用维度会造成实质性误读时，才在正文
  说明不可直接比较或相加。

## 8. 行业bundle固定块

行业章节只按已校验的`industry_bundle.status`写作，不从来源数量、段落是否写完
或叙述语气推断证据状态。固定块按下列逐行名称和顺序输出，不得合并或改名：

市场定义矩阵
历史市场规模与逐年增速
预测版本对照
集中度与竞争对手
当期部分期间
口径与数据限制

接受无歧义的industry bundle `schema_version: 1.0`作为向后兼容输入；新运行使用
`schema_version: 1.1`。v1.1的`market_definition_fingerprint`不含metric，
每个series另保留metric、unit、measurement basis和denominator对应的
`series_fingerprint`。读者正文只保留口径差异、缺失期间及其投资影响；
fingerprint、claim状态、role状态、route终态、schema版本和ledger路径，以及
`channel_scope`、`denominator`和lineage，必须紧跟对应块写入HTML注释，不得显示
在渲染正文中。机器引用属于同一表的证据记录，同样写入HTML注释。预测发布日期
和`data_vintage`是证据日期，不是forecast horizon；每个`data_vintage`单独
渲染一个series，严禁跨vintage拼接。

最后一块的可见内容只回答“哪些数据不可比或缺失，以及这会限制什么判断”；其HTML
审计注释另保留角色状态、逐claim的`claim_states`、缺失期间、
`missing_coverage`、ledger path、终态路由状态和下一步所需证据。
`claim_states`逐claim独立终止；accepted claim不得重新进入`unresolved_claims`
或重派。`partial`和`blocked`必须保留已接受evidence、periods和series，再单列
未覆盖内容。

所有数值表只从validated `accepted_candidates`填值；`industry_bundle`只决定
role状态、缺失期间和口径断点。历史块中的`行业驱动因素`子表只渲染
`industry-drivers` role的accepted evidence。

缺口行按机器字段直接映射：

- 口径断点依次取`scope_breaks[].from_scope_fingerprint`、
  `scope_breaks[].to_scope_fingerprint`和`scope_breaks[].reason`。
- route终态逐项取对应`ledger.attempts[].terminal_reason`。
- `blocked`先取`ledger.next_escalation`,为空时列出
  `ledger.unattempted_routes`。
- `exhausted`且没有下一route时写
  `new publication/data release required`。

状态写法：

- `complete`：正常填写六个固定块。
- `publishable-with-gaps`：保留已接受值，在正文逐年列出缺失期间及其投资影响，在
  HTML注释保存终态路由状态和下一步所需证据，并继续profile。
- `blocked`：保留已接受值，正文说明投资判断限制并标记需要人工跟进，逐route阻断
  状态只写入HTML注释；不得把阻断或未取得资料写成事实不存在。

## 9. 面向读者的正文

正文可以是一段自然完整的分析，不按固定句数或固定模板切割。正文的长度和结构由内容决定，不强制套用“结论、数据、风险”三段式，也不限制每节
只能写一句结论。先回答具体问题，再按需要给数据、表格和解释；可以写成一段，也可以
分成几段或列表。不为了显得正式而补齐过渡句、总结句或方法说明。删减的目标是去掉
无助于理解公司的文字，不是把每节机械压成固定句数。

### 9.1 让读者跟得上分析

遇到需要解释的变化，优先使用`数据 → 问题 → 原因 → 商业含义`的自然路径：

1. 先指出表里真正值得注意的变化或异常。
2. 提出读者也会关心的问题，例如增长来自哪里、毛利率为什么变化、扩张还有多少空间。
3. 给出公司解释、外部证据和自己的判断，不隐藏中间推理。
4. 最后说清它对盈利、竞争力、现金流或风险意味着什么；没有新增含义时不强行总结。

允许使用“先看”“更值得注意的是”“接着看”等自然衔接，也可以直接用问句推进分析。
这些词只在确实承接思路时使用，不作为每节重复出现的模板。正文不强制使用第一人称，
也不模仿宣传文、聊天记录或作者口头禅。

事实直接写；推断用“可能”“更可能”“还要看”等自然措辞标明边界。不要每句话都加
“证据支持”“尚不能形成结论”，也不要把未经验证的判断写成事实。

### 9.2 表格与正文分工

表格负责呈现结构和数字，正文负责解释这些数字对公司的意义：

- 表前用自然的一两句话说明分类维度、报告期或要回答的问题；简单表格一句即可。
- 不复述表格已经清楚呈现的层级、包含关系、合计或算术校验。
- 不逐行改写表格；从表里挑出集中度、变化趋势或异常值，再解释原因和商业含义。
- AI操作提醒、处理步骤和防错指令不得进入可见正文，应留在skill规则、隐藏注释或
  控制台输出中。

### 9.3 口径提示

口径提示也按读者价值取舍。只有在口径差异会实质改变比较或结论时，才用自然中文
说明限制，例如两个市场份额的市场范围或计量基础不同。若表题、列名、缩进或相邻
文字已经足以避免误读，就不再追加“不能相加”“同层级校验”“不要外推”等操作式
提醒。

例如，两张收入表分别展示IP归属和产品品类时，可以写：

> 下面按IP归属和产品品类分别列示2025年收入结构。

不要写：

> THE MONSTERS包含在艺术家IP中；毛绒、手办和MEGA属于另一套分类，两套占比不能
> 相加。

定稿前逐段自问：这句话是在帮助读者理解公司，还是只在提醒AI如何处理资料？只服务
后者的内容从可见正文删除。

### 9.4 证据缺口只说明一次

同一证据缺口只在最相关章节完整解释一次。例如公司份额序列缺年或计量口径变化，归入
竞争格局或成长空间；库存库龄缺失，归入财务风险。归口章节说明缺什么、影响哪项判断
即可。其他章节直接使用已经确认的数据，继续回答本节问题，不再复述缺失年份、口径变化
和搜索过程。不能陷入无止境的数据瑕疵重复描述。

数据不足时停止在简洁结论。若缺少的数据使本节无法形成有效分析，正文直接写“缺乏数据，无法分析”，
不展开检索失败、来源报错或底层缺项清单。若仍有部分事实可以支持判断，就写
已经确认的事实及其商业含义，不为了证明研究过程完整而罗列缺了什么。内部恢复信息继续留在隐藏字段，
不进入面向读者的正文。

子问题缺少数据时，写“<子问题>缺乏数据，无法分析”，然后继续本节其他分析；
不列举缺失字段、已查来源、旧年份样本或接口错误，句后不得继续解释缺什么或为什么没找到。
例如只写“客户画像缺乏数据，无法分析。”若该子问题不影响理解公司，可以直接省略，
不为了显示研究完整而补一句。

执行摘要只有在该缺口直接改变最终行动时才用一句自然中文概括，不重复技术细节。正文
不写“测试通过”“证据窗口完整”“连续序列未完成”等研究流程状态。

护城河来源写经济机制，例如品牌偏好如何支持溢价、多IP开发如何降低单一产品风险、
会员和直营渠道如何提高触达与反馈效率、规模采购如何影响成本。市场份额、毛利率和
资本回报是机制产生的结果或旁证，不是护城河来源本身；证据缺年更不是来源因素。

## 10. 问题驱动，而不是填模板

模板是查漏清单，不是文章提纲。框架提供问题库和分析工具，不提供现成答案。不同生意
的核心资产、利润变量、扩张约束和风险机制不同。不能把同一套分析顺序和指标机械套到所有公司。

开始写作前，先形成2-5个公司特有的关键问题。问题应来自业务结构、简化财务报表、跨年
变化和反常现象，例如利润为什么突然提高、现金为什么长期沉淀、增长受什么约束、扩张
为什么依赖收购。研究顺序由关键问题和新增证据决定，不按模板指导问题逐条抄题作答。
完成正文后再用模板反查漏项。

每个关键问题按实际需要展开：

- 先写观察到的事实，再追问原因；数字只在能推进理解时出现。
- 把事实、管理层解释、分析者判断和未知项分清。无需给每句话加标签，但不能把推测
  写成年报事实。
- 遇到陌生生意，可以与熟悉生意作比较。类比先帮助理解，再说明两者在哪里不同，
  不能因为表面相似就沿用结论。
- 小算术、单位经济和具体场景往往比抽象形容词更容易说明问题。计算过程保留到读者
  可以复核的程度，不展示无助于理解的中间步骤。
- 新证据推翻旧判断时，明确更正，并说明哪些结论随之改变；不要为了保持前后一致而
  隐藏错误。
- 风险按发生机制、发生可能性、影响程度和应对能力分析。优先讲真正会改变利润、现金
  流或治理判断的风险，不把所有风险等量罗列。

固定section仍需完整覆盖，但不重要的问题可以简洁交代，重要问题可以跨数据表深入
展开。最终文章应让读者看见“为什么会得出这个判断”，而不是只看到一组填完的字段。

## 11. 定稿格式与质量验收

### 11.1 Part 0执行摘要

好生意、护城河、管理层、财报排雷、能力圈、投资论点和三项主要风险统一使用
**状态标题 + 无前缀结论句 + 三色圆点证据**。结论单独放在引用块中，不写`一句话判断：`；证据使用`signal-list`和`signal-item`，绿色=正面、红色=负面、黄色=待验证。每条只表达一类判断，每块保留3-5条最关键证据，目标是让读者在
1-2分钟内看完主要结论和跟踪项。

Part 0结论块唯一标题为`### 执行摘要`，不得再套`### 结论速览`或`### 结论`。
状态项及顺序以template为唯一来源，不在单个profile中自造状态词。

### 11.2 引用和自引用

叙述段不使用句尾裸`(§x.y)`自引用，也不内嵌
`XXX(年报-YYYY.md p.NN)`式页码引用。普通叙述中的数字通过本节`**引用:**`
逐条映射到来源；紧凑数据表为避免映射歧义，可以在单元格直接写页码或URL。
两种方式都必须让数字唯一可追溯。规则指向句、`**引用:**`结构字段和skill规则
编号不属于正文自引用。

### 11.3 跟踪项和控制台信息

需要持续观察的项目使用`⚠️ **跟踪 N**:`或`⚠️ **注意**:`，不得把重要风险埋在
一般叙述中。运行时间、完成section数、文件路径、profile级置信度分布、AI免责声明
及其他runtime telemetry只输出到控制台，不进入profile。模板规定的机器流程字段和
Part 0内部工作流字段保留在Markdown的HTML注释中，由`reader-rendering.md`执行最终
投影和负向检查。

### 11.4 最终快扫

定稿前做一次母语中文和读者价值检查：删除翻译腔、重复heading、无助于理解公司的
方法说明、正文自引用、白名单外英文和运行元数据。Part 0应能在1-2分钟内读出全部
主要结论与跟踪项；做不到即视为输出质量未通过，修正后才可渲染。
